## 二、背景

这个插件要解决 pi 原生压缩的一个具体问题：原生摘要每次"在旧摘要上叠加"，多次压缩后摘要本身从 1k 膨胀到 17k token 以上，压缩后的起点越来越高，很快再次触线，形成反复压缩直至上下文涨满。

现插件（`pi-compact`，仓库 `newCompact-pi`）的做法是：每轮结束时先裁剪大工具结果（可用 `read_tool_result` 读回），仍超线才让模型**从零重写**一份 ≤8k token 的 8 段式状态快照，旧摘要归档到文件，再加快速重复压缩熔断与按 provider 实报用量的兜底触发。

本轮改造的出发点不是"再压小一点"，而是三个具体缺口：快照里没说清"哪些东西还能读回来"、原始请求在多次重写后可能走形、以及摘要输入里塞了大量无用内容导致成本随窗口填充度线性上升。

### 回退的改动

**增量门（growth gate）**：一度实现为"自上次压缩以来增长不足窗口 10% 就跳过压缩"，落在边界压缩与用量兜底两处，并配了 6 个单元测试。实现后判定为死代码，整体删除（`src/usage.ts`、`src/guard.ts`、`extensions/compact.ts`、`tests/boundary.test.ts` 的改动全部撤回，`tests/growth-gate.test.ts` 删除）。

原因：边界路径在门之前就有 `if (line <= 0 || total <= line) return skip("small")`，而压缩完成后 `total ≈ keepRecent + 快照` 必然低于触发线；用量兜底同样先被 `usageDecision` 的 `"small"` 拦住。也就是说门在正常流程里根本走不到。当时的单元测试是绿的，是因为用例**手动把基准值塞成接近 total** 才进入该分支——它证明"分支能跑"，不证明"特性会生效"。这是本轮最值得记下来的一条教训：**分支级单测无法证明可达性**。

## 五、依赖的 pi 内部事实（来源：本机 pi 1.4.0 源码，2026-11-02 阅读）

这几条决定了实现方式，列出来方便核对：

1. `core/agent-session.js`：手动与自动两条压缩路径都是先 `appendCompaction(...)`、再 `emit({type:"session_compact"})`。因此 `session_compact` 里取 `getBranch()` 已是压缩后的状态（本机实测确认）。
2. `sessionManager.getBranch()` 保留全部历史，压缩只是插入一个边界条目。因此"首条用户消息"始终是会话最初那条，多次压缩后仍可取到（用真实 `SessionManager` 实测确认）。
3. 压缩设置默认值：`reserveTokens = 16384`、`keepRecentTokens = 20000`（`core/settings-defaults.js`）。
4. `serializeConversation`（`core/compaction/utils.js`）只序列化 `user`/`assistant`/`toolResult` 三种角色；**thinking 块被丢弃**；工具结果截到 2000 char 且**只留开头**；toolCall 参数全文 `JSON.stringify` 进来。
5. `convertToLlm`（`core/messages.js`）把 `bashExecution`、`custom`、`branchSummary`、`compactionSummary` 统一映射成 `user` 文本消息，并会跳过标了 `excludeFromContext` 的 bash 执行。

## 六、按压缩场景回放出的问题

下面每条都是按"长会话 / 高填充 / 单轮暴涨 / 暂停后恢复 / 重复压缩 / 读归档"这几条路径走代码或实测得到的。

### 已修

| 问题 | 现象 | 影响 |
|---|---|---|
| **容量走廊只有 2% 窗口** | 容量检查是 `ceil((system + source) * 1.2) + 12288 + 4096 <= window`，而 `source` 是整段序列化对话。1M 窗口按此反解得到 source 上限 **819,680 token（82.0%）**，触发线却在 80% | 只有 20K token 的可用带；`triggerRatio ≥ 0.84` 等于插件静默失效；pi 原生 threshold（984K）与 overflow 路径**必然**过不了检查，退回原生摘要——正好是暂停后唯一还能救场的两条路径 |
| **投影消息丢失** | 新序列化器只认 `user`/`assistant`/`toolResult`，而 `prepareCompaction` 给的是投影消息 | 实测：一条 `bashExecution`（`!npm test`）和一条 `custom` 消息在新路径下整段消失，快照会缺 `!command` 的执行结果、注入消息、分支摘要 |
| **结构校验过严** | 要求 `## ` 行严格等于 8 个节名且顺序一致 | 多写一个 `## Notes`、或节内贴含 `## ` 的引用，整份快照作废并静默退回原生摘要（失败只在 `pi-compact.log` 可见） |
| **`insertBrief` 正则脆弱** | `^## Goal\n` 不匹配 `## Goal `（尾随空格）或末行无换行 | brief（主会话原始请求 / subagent 任务简报）静默丢失 |

### 未修（已确认存在，留作下一轮）

| 问题 | 现象 | 建议 |
|---|---|---|
| **首次压缩指向不存在的归档**（本次 CR 新发现，HEAD 已有） | `archived = !preparation.previousSummary` 在没有上次摘要时直接为 true，但那段代码只在有上次摘要时才写文件；实测首次压缩的快照里出现 `Older details: <path>` 与 `older snapshots in <path>`，而 `existsSync(archivePath)` 为 false | 把 `archived` 三态化（`archived` / `none`（首次，本无归档）/ `failed`），首次不输出归档指针；同时把 benchmark `claude-code#7502` 拆成首次/后续两个场景（现在这条断言把首次的假指针固化成了期望行为） |
| **可恢复但无地址** | 快照说被裁工具结果可用 `read_tool_result(entryId, …)` 读回，但那些 entry id 只存在于被压缩掉的文本里，压缩后快照中没有任何 id | 压缩时扫摘要范围内的 `context_edit` 条目，把 `targetId + 工具名 + 原大小` 作为 ≤100 token 的清单（不带 `## `）追加进快照；数据都在 `branchEntries` 里，不需要调模型 |
| **归档无上限、读取被截断** | `compaction-archive/<sessionId>.md` 每次压缩追加一份旧摘要；10 次压缩后 >300KB，而 `read` 默认截断在 2000 行 / 50KB | 归档滚动保留最近若干份，或在恢复点写明"最新的在文件末尾，用 offset 读" |
| **单轮内暴涨可跳过边界** | 裁剪器只在 `turn_end` 生效，若一轮内因大文件/大输出把 total 从 80% 以下推到 98% 以上，边界压缩没机会跑，直接进 pi 原生 threshold | 已知限制；若要在轮内处理，需要在 `tool_result` 或请求前裁剪，但那会改动缓存前缀，需单独评估 |
| **暂停状态会关掉插件** | 熔断暂停后边界路径不再跑，只剩原生 threshold / overflow；这两条在 1M 窗口下过不了容量检查（本轮已用降档缓解，但 tight 也有上限） | 降档后已大幅缓解；建议再加"暂停期间仍允许 boundary，但只做 tight 档"的策略评估 |

## 七、成本：摘要输入的结构与实测

摘要输入 = `previous-summary` + 序列化的"上次压缩以来的增量"。因为每条消息一生只被摘要一次，**总摘要成本 ≈ 会话总 token × 单价**，与压缩次数无关（提高触发线只改变"何时付钱"）。

pi 已经省掉两件事：thinking 不序列化；工具结果截到 2000 char。剩下三块构成（三个本机真实会话，按 pi 规则复现）：

| 部分 | 占比 |
|---|---|
| 工具结果 | 41–55% |
| toolCall 参数 | 24–32% |
| assistant 正文 | 21% |
| user | 0.4–5% |

toolCall 参数里 **bash 占 73%**（长 heredoc、`curl`、`bun -e` 脚本），write+edit 占 12%。也就是说 pi 的序列化会把 `write`/`edit` 的文件正文和 bash 脚本全文塞进摘要输入。

改造后（`bun scripts/eval-serialize.ts <session.jsonl>` 实测）：

| 会话 | pi 原生 | 新 full 档 | 新 tight 档 |
|---|---|---|---|
| 会话 A（220 msg） | 48,750 | 31,798（−35%） | 24,088（−51%） |
| 会话 B（182 msg） | 41,160 | 25,392（−38%） | 16,114（−61%） |
| 会话 C（294 msg） | 72,804 | 37,531（−48%） | 23,512（−68%） |

金额量级（DeepSeek flash 输入 $0.3/M，来源：本机 `models-store.json`）：单次压缩成本完全取决于触发时的填充度——三个会话这个体量单次约 $0.012–0.02；1M 窗口贴着 80% 触发时约 $0.23/次。所以短会话可忽略，长会话才是主要开销，而降幅正好落在这部分。

需要说明的局限：这三个会话的 toolCall 参数里 bash 占比异常高（因为当天大量用 `bun -e` 做测量），真实编码会话里 `write`/`edit` 的占比应该更高，收益方向一致但比例会变。

## 八、未验证与风险

- **摘要质量没有量化**：截断一定损失信息，但因为被裁的工具结果仍可从原文读回、bash 保留头尾（错误通常在尾部），判断是可接受的。真正应该做的是信息留存率探针：取真实会话，在压缩点后问 N 个只能靠被压掉内容回答的问题，比较 不压缩 / 快照 / 快照+恢复提示 的正确率。**尚未做**，这也是 benchmark 里唯一没有覆盖的维度。
- **归档写入时机提前的副作用**：为了让「归档是否成功」影响快照文本，归档写从函数末尾挪到了第一次模型调用之后。若随后因超 8k 走 condense 再失败，会留下一条没人引用的归档片段，下次成功压缩时同一份旧摘要可能被再追加一次。归档仅作诊断依据，不影响快照正确性，但会加快归档增长（与下面「归档无上限」叠加）。更干净的做法：仍在本末尾写归档，失败时用已知的模型输出重新拼一份 `archived=false` 的快照。**未改**，留作 review 决策。
- **tight 档的实际触发频率未知**：只验证了它能被触发且不额外调用模型，没有统计在真实长会话里占多少比例。
- **`convertToLlm` 对 `branchSummary` / `compactionSummary` 的映射只读了源码**，实测覆盖的是 `bashExecution` 与 `custom`。
- **降档与校准的相互作用未知**：容量检查用的是 `textTokens` 粗估，实际 token 数由 provider 决定，1.2 的系数是经验值，没有按模型校准。
- **`--exclude-tools` 关掉 `read_tool_result` 的场景**：快照里的可恢复段落会指向一个不存在的工具（已改为"when that tool is enabled"的措辞，但没有真机验证）。
- **归档滚动未实现**，长会话里归档会被 `read` 截断。
- 本机没有 `@types/node`，类型检查只能人工筛；仓库也没有 CI 配置，测试靠本地 `bun test`。

## 九、给 review 的四个问题

1. **序列化截断该不该按工具类型分档？** 现在统一 300 / bash 500。是否值得为 `write`/`edit` 更狠（只留路径 + 前 80 字）、为 `read` 只留路径？这样能再降一档，但摘要模型看到的信息更少。
2. **容量处理用"两档 profile"是否足够？** 另一条路是按消息逐条裁剪并写 `[elided: entry x..y]`（需要把消息映射回 entry id）。当前选择是"更少的代码、无新映射"，代价是 tight 档仍可能不够。哪种更符合这个项目的取舍？
3. **静默退回 pi 原生摘要是否该有用户可见信号？** 现在所有 fallback 只进日志（`~/.pi/agent/pi-compact.log`）。连续多次 fallback 时是否该像暂停那样给一条 status / notify？
4. **8 节 6k 预算对 1M 窗口是否太小？** 长会话里早期事实只能靠归档；如果快照预算随窗口按比例放大（比如 1M 窗口给 12k），成本增加有限但撤回风险更低。这需要质量数据支撑，目前没有。
